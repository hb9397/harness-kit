## 문서 루트 계약

이 스킬이 하네스 문서를 읽거나 쓸 때 사용하는 정본은 `.ai-docs/`뿐이다. `.docs/`
디렉토리가 존재해도 참조하지 않고 일반 디렉토리로 취급하며, 호환 별칭으로 추측하지
않는다. 애플리케이션 소스 작업 자체의 권한과 가능 여부는 이 문서 루트 판정으로
제한하지 않는다.


# 프론트엔드 디자인 (frontend-design)

이 스킬은 클리셰 UI를 피하고, 맥락에 맞는 개성 있는 프론트엔드 구현을 목표로 한다.
결과물은 실제로 동작하는 프로덕션급 코드여야 한다.

제품 소스 변경 범위와 앱 소유권은 단일 앱의
`@.ai-docs/instruction/artifact-output-routing-instruction.md` 또는 복수 앱의
`@.ai-docs/{앱}/instruction/artifact-output-routing-instruction.md`를 확인한 뒤
승인된 앱 소스에만 반영한다.

## 진입 라우팅

작업을 시작하기 전에 요청의 최종 산출물을 기준으로 다음 중 하나만 선택한다.

| 사용자의 최종 산출물 | 정규 처리 | 제공 스킬 예시 |
|---|---|---|
| 화면 구조·요구사항·흐름을 담은 Markdown 설계 문서 | prototype 문서 경로 | `design-prototype-docs` |
| `.ai-docs/prototype/` 아래에서 폐기 가능한 HTML/CSS/JS 검증 시안 | prototype bundle | `create-prototype` |
| 애플리케이션 소스에 반영할 페이지·컴포넌트·스타일 | 승인된 앱 source root | `frontend-design` |

요청에 “화면”, “UI”, “프로토타입”이라는 단어가 있다는 이유만으로 선택하지 않는다.
현재 요청이 문서나 검증 시안이면 선택한 producer로 handoff하고 이 스킬의 프로덕션
코드 수정 단계는 실행하지 않는다. 제공 스킬 이름은 선택지이며 다른 도구를 배제하지 않는다.

---

## 선행 입력

위 라우팅 표는 **최종 산출물**로 담당을 가른다. 아래는 이 스킬이 구현을 시작하기
전에 받는 **입력**이며 축이 다르다. 디자인과 모션은 출처가 다르므로 따로 본다.

| 축 | 1순위 | 2순위 | 입력이 없을 때 |
|---|---|---|---|
| 디자인 | 기존 제품의 디자인 시스템·컴포넌트·토큰 | 승인된 `ui-ux-pro-max` 결정 | 아래 구현 기준 |
| 모션 | 기존 제품의 모션 언어 | 승인된 `motion-design` 명세 | 접근 가능한 최소 상태 피드백 |

1순위와 2순위가 충돌하면 **구현하지 말고** 차이와 근거를 보고한다. 제품 코드의
현실이 설계 제안보다 우선한다.

프로토타입 코드는 재사용하지 않는다. `.ai-docs/prototype/**`에서 복사하지 말고
승인된 디자인 결정과 화면 명세만 다시 해석해 제품 구조에 맞게 구현한다.

## STEP 0 — 프로젝트 유형 확인 (C-1 확인 단계)

구현 범위를 확정하기 위해 **반드시** 아래를 수행한다.

1. 현재 수행 위치에서 프로젝트 구조를 탐색한다 (git repo 경계, 하위 앱 폴더 후보 스캔).
2. **단일 애플리케이션 프로젝트**인지 **복수 애플리케이션 프로젝트**인지 판정한다.
3. 판정 결과 + 구현 대상 애플리케이션(폴더)을 사용자에게 **반드시 재확인**한다.
4. **작업 대상 구분** — 실제 소스코드의 앱 디렉터리와 컴포넌트/페이지 범위를 확인한다.
   프로토타입이나 설계 문서로 확인되면 위 진입 라우팅에 따라 handoff한다.
5. 확인된 범위 밖은 건드리지 않는다.
6. 기존 프로젝트/디자인 시스템이 있으면 해당 규칙을 우선 존중한다.

## 설계 사고

코딩 전에 아래를 먼저 결정한다.

- **목적**: 이 인터페이스가 해결하는 문제와 사용자
- **톤**: 하나의 방향을 명확히 선택 (미니멀, 맥시멀, 레트로, 산업적 등)
- **제약**: 프레임워크, 성능, 접근성 요구사항
- **차별화 포인트**: 사용자가 기억할 핵심 1가지

원칙: 방향을 정했으면 끝까지 밀어붙인다. 핵심은 강도가 아니라 의도성과 일관성이다.

## 금지 패턴

- Inter, Roboto, Arial, 시스템 기본 폰트 중심 구성
- 보라색 계열 그라데이션 + 흰 배경 클리셰
- 맥락 없이 반복되는 카드/히어로/버튼 보일러플레이트

## 구현 기준

구현 시 아래를 반드시 지킨다.

- 타이포그래피: 목적 있는 폰트 조합, 기본 스택 회피
- 색상: CSS 변수 기반 팔레트 정의, 분명한 시각 방향 유지
- 모션: `motion-design` 명세가 있을 때만 해당 모션을 구현한다. 명세가 없으면
  상태 피드백에 필요한 최소 전환만 두고 장식 애니메이션을 추가하지 않는다.
- 배경/질감: 단색 배경 대신 깊이감(그라디언트, 패턴, 레이어) 부여
- 완성도: 데스크톱/모바일에서 레이아웃이 깨지지 않도록 검증

## 출력 원칙

- 요구사항이 불명확하면 최소 질문으로 맥락만 보완하고 바로 구현한다.
- 결과 코드는 즉시 실행 가능한 형태로 제공한다.
- 기존 프로젝트/디자인 시스템이 있으면 해당 규칙을 우선 존중한다.

## 구현 검증

기능·UI·접근성·모션을 요구사항 기준으로 추가 검증하려면 `impl-verify` 또는 동등한
검증 도구를 선택할 수 있다. 아래는 어떤 후속 도구를 선택하든 이 스킬이 구현을 마치기
전에 직접 수행하는 최소 확인이다.

완료 전 프로젝트가 제공하는 검증 명령을 우선 사용한다.

1. 변경한 앱의 formatter·lint·typecheck·test·build 명령을 탐색한다.
2. 안전하게 실행 가능한 자동 검증을 수행하고 결과를 기록한다.
3. 브라우저 또는 렌더링 도구가 있으면 목표 viewport와 모바일 viewport를 확인한다.
4. 키보드 focus, 명도 대비, reduced-motion, overflow와 주요 상호작용을 점검한다.
5. 실행하지 못한 검증은 통과로 간주하지 않고 이유와 수동 확인 절차를 보고한다.
