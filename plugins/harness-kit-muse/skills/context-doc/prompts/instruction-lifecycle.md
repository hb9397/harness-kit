# instruction 파일 생성·갱신·삭제 기준

`context-doc`이 앱별 `*-instruction.md`의 생명주기를 판정할 때 사용하는 계약이다.
주제별 실제 규칙의 분류는 `analysis-instruction.md`를 따르고, 이 문서는 파일의 생성 상태와
현재성만 다룬다.

## 라우팅 표

| 상황 | 적용 섹션 |
|---|---|
| 앱 instruction 최초 생성 | [최초 생성] + [초기 기본 세트] |
| 기존 instruction 갱신 | [현재 규칙으로 갱신] |
| 더 이상 필요하지 않은 파일 발견 | [불필요 파일 삭제] |

## 현재 사실 전용 계약

- `{앱}-context.md`와 모든 `*-instruction.md` 본문에는 현재 확인되거나 사용자가 확정한
  사실·규칙만 둔다.
- 과거 값, 변경 전 규칙, 추가·수정·삭제 경과, 날짜별 기록, `변경 이력`·`History`·
  `Changelog` 섹션을 산출물 본문에 만들지 않는다.
- 기존 문서를 갱신할 때 폐기된 규칙은 새 규칙 옆에 보존하지 않고 제거한다. 변경 이유와
  삭제 후보는 저장 전 검토 화면에서만 보여준다.
- Git 기록, 승인 기록, 외부 bundle manifest처럼 별도 운영 계약이 요구하는 증적은 해당
  전용 저장소에 남길 수 있지만 앱 context나 주제별 instruction 본문에 복제하지 않는다.

## 초기 기본 세트

참조 앱에서 반복적으로 필요했던 다음 파일을 앱 instruction의 초기 기본 세트로 사용한다.

| 상태 | 파일 | 최초 본문 |
|---|---|---|
| 항상 유지 | `agent-instruction.md` | 제목·보편 목적·포함 주제 설명만 둔 골격 |
| 항상 유지 | `artifact-output-routing-instruction.md` | 실행 가능한 공용 routing 계약 |
| 초기 후보 | `architecture-instruction.md` | 제목·보편 목적·포함 주제 설명만 둔 골격 |
| 초기 후보 | `data-standard-instruction.md` | 제목·보편 목적·포함 주제 설명만 둔 골격 |
| 초기 후보 | `code-style-instruction.md` | 제목·보편 목적·포함 주제 설명만 둔 골격 |
| 초기 후보 | `framework-instruction.md` | 제목·보편 목적·포함 주제 설명만 둔 골격 |
| 초기 후보 | `file-convention-instruction.md` | 제목·보편 목적·포함 주제 설명만 둔 골격 |
| 조건부 확장 | `api-instruction.md` | HTTP API에 독립해서 반복 적용할 현재 규칙이 확인될 때 같은 형식의 골격 |
| 조건부 확장 | `comm-instruction.md` | 비-HTTP 통신에 독립해서 반복 적용할 현재 규칙이 확인될 때 같은 형식의 골격 |

팀 고유 instruction은 현재 앱에 적용되는 근거가 있을 때만 별도 후보로 추가한다.

## 최초 생성

1. `agent-instruction.md`와 `artifact-output-routing-instruction.md`는 기존 계약대로 항상
   생성한다.
2. 다섯 초기 후보를 함께 생성한다. `api`와 `comm`은 해당 통신 방식의 존재만으로 만들지
   않고 독립해서 반복 적용할 현재 규칙이 확인될 때만 생성한다.
3. `artifact-output-routing-instruction.md`를 제외한 최초 파일에는 앱별 세부 규칙을
   추측해 채우지 않는다. 제목과 `>` 인용문으로 문서의 정본 역할과 보편적으로 담는
   주제만 설명하고, 규칙 본문은 비워둔다.
   인용문에는 실제 앱 이름과 현재 기술 스택에서 확인한 적용 표면을 사용한다. 예를 들어
   데이터 표준 문서는 문서·소스·DDL처럼 실제로 존재하는 대상을 열거하되 확인되지 않은
   언어·프레임워크·저장소 기술은 넣지 않는다.
4. 빈 표, `[규칙]`, `미정`, 범용 모범 사례를 현재 앱 규칙처럼 넣지 않는다.
5. 앱 context 9번에는 실제 생성 파일을 모두 연결하고 현재 상태를 `목적만 정의됨` 또는
   `적용 중`으로 구분한다. 목적만 정의된 골격은 프로젝트 규칙의 근거로 사용하지 않는다.

## 현재 규칙으로 갱신

- 이후 입력, 현재 DESIGN, 코드·설정, 승인된 팀 표준에서 주제별 규칙이 확인되면 해당
  골격을 현재 규칙으로 교체한다.
- 보편 목적 인용문은 유지하되 기술명·적용 범위는 현재 앱에 맞게 구체화할 수 있다.
- 하나의 규칙에는 현재 패턴과 적용 범위만 둔다. 금지 규칙은 현재 금지 패턴·이유·대안이
  모두 확인된 경우에만 기록한다.
- 부분 근거나 미확정 규칙은 instruction 본문에 `미정`으로 쌓지 않고 검토 화면의 보강
  후보로만 제시한다.

## 불필요 파일 삭제

- 재실행할 때 항상 유지 파일을 제외한 모든 instruction의 현재 필요성을 다시 판정한다.
- 현재 DESIGN·코드·설정·승인된 표준 어디에도 적용 근거가 없고 앞으로 읽을 조건도 없는
  파일은 삭제 후보로 분류한다. 단순히 본문이 짧다는 이유만으로 삭제하지 않는다.
- 삭제 후보와 근거, 앱 context 9번에서 함께 제거할 링크를 저장 전 미리보기에 명시한다.
  권한 확인과 사용자 승인을 받은 뒤 파일과 인덱스 행을 같은 변경에서 제거한다.
- 삭제된 파일명이나 과거 내용을 앱 context와 남은 instruction 본문에 기록하지 않는다.
- `agent-instruction.md`와 `artifact-output-routing-instruction.md`는 삭제 후보가 아니다.
