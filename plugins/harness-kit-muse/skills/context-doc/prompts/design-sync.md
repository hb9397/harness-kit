# DESIGN.md ↔ 애플리케이션 컨텍스트 동기화

`context-doc`이 대상 앱의 `DESIGN.md`와 `.ai-docs/{앱}-context.md`를 양방향으로
추적할 때 사용하는 동기화 계약이다. 두 문서는 역할이 다르므로 같은 내용을 전부
복제하지 않는다.

## 라우팅 표

| 상황 | 적용 절차 |
|---|---|
| 앱 컨텍스트 최초 작성 | [최초 작성] |
| 기존 앱 컨텍스트 갱신 | [기존 문서 갱신] |
| DESIGN.md와 코드·설정이 충돌 | [충돌 처리] |

## 공통 역할

- `DESIGN.md`는 앱의 개요, 상위 기능 분류, 기술 스택, 선택한 아키텍처, 앱 고유 경계와
  배포 방향을 공유하는 상위 설계 정본이다.
- `{앱}-context.md`는 해당 `DESIGN.md`와 현재 애플리케이션 소스·설정·Git 정보를
  AI가 구현 중 바로 사용할 수 있는 상세 사실과 지침 인덱스로 전개한다.
- 앱 컨텍스트는 `DESIGN.md`를 대체하지 않고, `DESIGN.md`도 실행 프로필·Git remote·
  환경 변수 같은 상세 운영 사실을 모두 복제하지 않는다.

## 공통 주제 매핑

| DESIGN.md 또는 현재 자료 | 애플리케이션 컨텍스트 |
|---|---|
| 제목·요약, 01 개요 | 제목·요약, 1 프로젝트 개요 |
| 02 구축 대상 기능 분류 | 10 구축 대상 기능 분류 |
| 03 기술 스택 | 2 기술 스택 |
| 04 아키텍처 | 3 아키텍처 |
| 실행 profile·명령·엔트리포인트 | 4 실행 프로필 및 실행 방식 |
| Git config·HEAD·refs | 5 Git 원격 저장소 및 브랜치 |
| 06 배포 환경과 현재 배포 설정 | 6 배포 방식 |
| 05 애플리케이션 특이사항, 기존 앱 고유 사실·핵심 도메인 개념 | 7 애플리케이션 특이사항의 계층형 하위 노드 |
| 환경 설정·코드에서 참조하는 환경 변수 | 8 애플리케이션 사용 환경 변수 목록 |
| 실제 instruction 파일과 적용 조건 | 9 AI 구현 지침 |

`DESIGN.md`의 VSCode 익스텐션 추천은 애플리케이션 고정 컨텍스트에 복제하지 않는다.
특정 확장의 사용이 실제 구현 규칙이라면 해당 instruction에서만 다룬다.

## 최초 작성

1. 대상 앱과 정확히 대응하는 `DESIGN.md`를 먼저 읽는다.
2. 현재 매니페스트·소스·실행 설정·배포 설정·Git metadata·기존 instruction을 읽는다.
3. 상위 설계 사실은 `DESIGN.md`, 상세 실행 사실은 현재 코드·설정·Git 근거로 채운다.
4. 제목 바로 아래에 기준 `DESIGN.md`의 `@` 경로와 Markdown 링크, 문서 역할,
   양방향 최신화 원칙을 기록한다.
5. 루트 컨텍스트 → 앱 컨텍스트 → 필요한 instruction 순서도 최상단에 기록한다.

## 기존 문서 갱신

1. 기존 앱 컨텍스트 전체를 현재 사실 후보로 읽고 새 1~10 목차에 의미 기준으로 배치한다.
2. 기존 `핵심 도메인 개념`은 7번의 `### 핵심 도메인 개념` 아래에 의미와 관계 중심의
   하위 노드로 옮긴다. 명명·약어·코드값 규범은 기존 또는 새
   `data-standard-instruction.md`로 분리하고 9번 인덱스에서 연결한다.
3. 기존 `실행 방법`은 DB 명령을 제외하고 4번의 profile별 애플리케이션 실행 정보와
   6번의 환경별 배포 정보로 분리한다.
4. 기존 `환경 설정`의 환경 변수는 8번으로 옮기되 실제 비밀 값은 기록하지 않는다.
5. 기존 `프로젝트 고유 주의사항`과 `DESIGN.md`의 같은 주제는 현재 유효한 사실만
   7번에서 합친다.
6. 기존 instruction 인덱스는 실제 파일과 적용 여부를 다시 확인해 9번에 `@` 경로와
   현재 파일 기준 Markdown 링크를 함께 기록한다.
7. 기존 기능 분류는 DESIGN.md 02와 대조해 10번에 같은 노드명·순서·부모-자식 관계·
   Depth로 재구성하고, 현재 구현 대응은 별도 연결 표에 기록한다.

## 구축 대상 기능 분류 양방향 추적

- DESIGN.md 02는 상위 기능 분류 정본이고 앱 컨텍스트 10은 같은 트리를 구현 탐색용으로
  전개한 추적 뷰다.
- 앱 컨텍스트 10의 분류 트리는 DESIGN.md 02보다 독립적으로 깊어지거나 평탄화되지 않는다.
- 현재 코드·상세 문서에서 DESIGN에 없는 분류가 확인되면 현재 불일치를 검토 화면에
  표시하고 공개 `design-doc` workflow로 노드의 추가·이동·이름·Depth 확인을 요청한다.
- DESIGN.md 02가 승인 갱신되면 앱 컨텍스트 10의 트리와 구현 연결을 같은 실행에서 다시
  대조한다. 어느 문서에도 추가·이동·삭제 이력은 남기지 않는다.

## 충돌 처리

다음 우선순위로 현재 상태를 판정하되 서로 다른 역할의 정본을 조용히 덮어쓰지 않는다.

1. 이번 실행에서 사용자가 확정한 내용
2. 현재 애플리케이션 코드·매니페스트·설정·배포 파일과 Git metadata
3. 현재 `DESIGN.md`의 상위 설계 결정
4. 위 근거와 충돌하지 않는 기존 앱 컨텍스트

- 코드·설정에서 확인한 현재 사실이 앱 컨텍스트와 다르면 앱 컨텍스트 초안을 갱신한다.
- 차이가 `DESIGN.md`의 개요·기능 분류·기술 스택·아키텍처·앱 특이사항·배포 방향에도
  영향을 주면 변경 이유와 근거를 검토 화면에 표시하고 공개 `design-doc` workflow로
  해당 상위 설계의 갱신을 제안한다.
- `context-doc`이 `DESIGN.md`를 직접 고치거나 상위 설계 결정을 추측하지 않는다.
- `DESIGN.md`가 갱신되면 다음 `context-doc` 실행에서 대응 섹션을 다시 비교한다.
- 저장 본문에는 변경 전 값, 추가·삭제·이동 이력, 날짜별 경과를 남기지 않고 현재
  유효한 사실만 기록한다.
