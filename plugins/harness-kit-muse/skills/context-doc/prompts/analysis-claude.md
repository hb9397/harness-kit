# 애플리케이션 컨텍스트 추출 기준

`.ai-docs/{앱}-context.md`는 대상 앱의 `DESIGN.md`와 현재 소스·설정·Git 정보를
AI가 구현 중 바로 사용할 수 있도록 전개한 상세 애플리케이션 컨텍스트다. 루트
`AGENTS.md`와 `.ai-docs/root-context/**`에는 이 분석 결과를 직접 쓰지 않는다.

## 라우팅 표

| 입력 상태 | 적용 기준 |
|---|---|
| PROJECT_DESIGN 형식 DESIGN.md | [공통 추출] + [1~10 섹션] |
| 기존 앱 컨텍스트 갱신 | [공통 추출] + `prompts/design-sync.md`의 기존 문서 갱신 |
| harness-bootstrap 관찰 인벤토리 포함 | [관찰 기반 입력] 추가 적용 |

## 공통 추출

- 대상 앱과 정확히 대응하는 `DESIGN.md`를 항상 먼저 읽는다.
- 상위 설계는 `DESIGN.md`, 상세 실행 정보는 현재 매니페스트·소스·설정·배포 파일,
  Git metadata와 기존 instruction에서 확인한다.
- 현재 확인되거나 사용자가 확정한 사실만 쓴다. 변경 이력과 과거 값을 누적하지 않는다.
- 자격 증명, token, private key, 환경 변수의 실제 비밀 값과 인증정보가 포함된 Git URL은
  기록하지 않는다. Git URL에는 provider·host·repository 식별에 필요한 값만 남긴다.
- 규칙과 금지 목록은 주제별 instruction으로 분리하고, 앱 context에는 애플리케이션
  사실과 instruction 탐색 정보만 둔다.

## 제목과 최상단 읽기 계약

- 제목은 `# [프로젝트명] [FE/BE/전체] — AI Agent Guide` 형식을 사용한다.
- 제목 바로 아래에 기준 `DESIGN.md`의 정규화한 `@` 경로와 현재 문서 기준 상대 링크를
  함께 둔다.
- 이 문서가 `DESIGN.md`를 AI 구현용 상세 컨텍스트로 전개하며 두 문서의 공통 주제를
  양방향으로 추적·최신화한다는 점을 명시한다.
- 기존 개요 요약 한 줄을 유지한다.
- 루트 컨텍스트 `@AGENTS.md` → 현재 앱 컨텍스트 → 9번에서 판단한 필요한 instruction의
  순서로 읽고, 관련 instruction은 구현 전에 반드시 읽도록 최상단에 명시한다.

## 1. 프로젝트 개요

- `DESIGN.md`의 개요를 기준으로 앱의 목적·사용자·환경을 맞춘다.
- 현재 구현된 주요 동작, 외부 연동과 아직 구현되지 않은 앱 기능을 상세 사실로 보완한다.
- 기능 분류를 상세 문서나 구현의 허용 목록으로 해석하지 않는다.

## 2. 기술 스택

- `분류 | 기술 | 버전·기준` 표를 유지한다.
- `DESIGN.md`의 기술 스택과 현재 매니페스트·빌드 설정을 대조한다.
- 언어·프레임워크·통신·파서·빌드·로깅처럼 앱 구현에 직접 쓰이는 기술을 기록한다.
- 제안 단계의 기술은 확정 기술처럼 쓰지 않는다.

## 3. 아키텍처

- `DESIGN.md`에서 사용자가 선택한 상위 패턴과 현재 선택 근거를 기록한다.
- 현재 소스에서 역할이 있는 패키지·파일만 추린 트리를 기록한다.
- 레이어 의존 방향과 금지 규칙은 `architecture-instruction.md`로 분리한다.

## 4. 실행 프로필 및 실행 방식

- 사용자가 별도 profile을 지정하지 않고 현재 설정에서도 다른 이름이 확인되지 않으면
  `local`, `dev`, `prod`를 기본 profile로 제시한다. `local`은 로컬 개발, `dev`는
  개발·검증 서버, `prod`는 운영 용도로 구분한다.
- profile별 용도, 활성화 방법, 애플리케이션 실행 명령, 포트·엔트리포인트와 동작
  차이를 기록한다.
- DB 생성, schema migration, seed, DB 접속·검증 명령은 기록하지 않는다.
- 애플리케이션 실행과 직접 관계없는 인프라 운영 절차는 6번에도 추측해 넣지 않는다.

## 5. Git 원격 저장소 및 브랜치

- 대상 앱의 실제 Git 경계를 먼저 확정한다.
- `.git/config` 또는 동등한 현재 Git metadata에서 remote 이름과 URL을 확인하고,
  `.git/HEAD`, refs와 packed refs에서 현재·추적 branch를 확인한다.
- URL의 사용자정보·token·credential·민감 query는 제거한다.
- 사용자나 저장소가 환경별 branch 매핑을 별도로 정하지 않았다면 `dev`, `main` branch를
  기본 기준으로 제시한다. `dev` branch는 실행 profile `dev`,
  `main` branch는 실행 profile `prod`에 대응시키고 `main`을 운영 branch로 취급한다.
  `local`에는 환경별 branch를 배정하지 않으며, 실제 원격 존재를 확인하지 못한 branch를
  현재 존재하는 branch로 표현하지 않는다.

## 6. 배포 방식

- 로컬 PC, 개발 서버, 운영 서버를 구분한다.
- Kubernetes manifest가 있으면 workload·image·ConfigMap/Secret 주입과 실행 단위를,
  Dockerfile·Containerfile이 있으면 image 빌드·실행 단위를, JAR·WAR·정적 산출물이면
  build 결과물과 실행·제공 방식을 현재 파일 근거로 기록한다.
- 환경별 서버 형태, OS·runtime, 배포 단위와 실행 방식을 기록한다.
- DB 설치·기동·migration 절차는 이 섹션에 기록하지 않는다.

## 7. 애플리케이션 특이사항

- `DESIGN.md`의 상위 특이사항을 평면 복제하지 않고 기존 앱 컨텍스트와 현재 앱 자료의
  상세 사실을 `###` 대분류와 `####` 세부 주제의 계층형 노드로 조직한다.
- `### 핵심 도메인 개념`을 고정 하위 노드로 두고 개념의 의미·관계·주요 식별자를
  `####` 묶음 아래에 기록한다.
- 그 밖의 앱 고유 연동·데이터 처리 경계·스케줄·호환 동작·운영 제약도 주제별 하위
  노드로 기록한다.
- 일반 코딩 조언과 다른 섹션의 중복은 제외한다.
- 변경 과정이 아니라 현재 유효한 상태와 규칙만 남긴다.

## 8. 애플리케이션 사용 환경 변수 목록

- 환경 설정 파일과 코드가 실제로 참조하는 환경 변수만 기록한다.
- 변수명, 적용 profile, 용도, 필수·비밀 여부와 비밀이 아닌 기본값 또는 주입 출처를
  표로 작성한다.
- 실제 token·비밀번호·인증키 값은 마스킹 값조차 복제하지 않고 기록하지 않는다.

## 9. AI 구현 지침

- 실제 instruction root를 탐색해 현재 존재하고 대상 앱에 적용되는 instruction을 모두
  후보로 수집한다. 표준 카탈로그 밖의 팀 고유 instruction도 현재 유효하면 보존한다.
- 각 행에 주제, 정규화한 `@.ai-docs/...` 참조, 현재 앱 context 기준 Markdown 상대 링크,
  현재 상태(`적용 중` 또는 `목적만 정의됨`)와 이 지침을 읽어야 하는 작업 조건을 기록한다.
- 존재하지 않는 파일, 다른 앱 instruction과 깨진 링크는 넣지 않는다.
- 목적만 정의된 최초 골격은 현재 프로젝트 규칙의 근거로 사용하지 않으며, 불필요 판정으로
  삭제된 파일은 같은 실행에서 인덱스에서도 제거한다.
- `agent-instruction.md`는 항상 읽도록 표시한다. 산출물을 만들거나 옮기는 작업은
  `artifact-output-routing-instruction.md`를 반드시 읽도록 표시한다.
- 루트 컨텍스트 → 앱 컨텍스트 → AI가 작업에 필요한 instruction 판단 → 해당 문서 필독
  순서를 이 섹션에서도 다시 명시한다.

## 10. 구축 대상 기능 분류

- `DESIGN.md`의 `02. 구축 대상 기능 분류`와 같은 노드명·순서·부모-자식 관계·Depth를
  유지한 기능 분류 트리를 기록한다.
- 분류 트리와 별도로 각 분류 경로의 현재 구현 상태, 관련 패키지·파일·상세 문서와
  동기화 판정을 기록한다.
- 이 분류는 탐색과 구현 연결을 위한 목차이며 상세 문서나 구현의 허용 목록이 아니다.
- 현재 코드나 상세 문서에만 있는 기능 분류는 앱 컨텍스트에서 독립적으로 추가하지 않고
  drift로 표시해 공개 `design-doc` workflow에서 노드와 Depth를 확인한다.
- DESIGN.md 02가 갱신되면 10번 트리와 구현 연결을 다시 대조하고 현재 구조만 남긴다.

## 제외·재배치 항목

- `핵심 도메인 개념`을 독립된 최상위 섹션으로 만들지 않고 7번의 계층형 하위 노드로
  배치한다.
- 도메인 개념의 의미와 관계는 7번, 명명·약어·식별자 표현·코드값 규범은 조건부
  `data-standard-instruction.md`로 분리하고 9번에서 연결한다.
- API·WebSocket endpoint 목록은 앱의 현재 동작 이해에 꼭 필요할 때만 1번이나 7번에
  짧게 기록하고, 상세 규약은 관련 instruction으로 분리한다.

## 누락 항목 처리

- `DESIGN.md` 자체가 없으면 앱 context를 정본으로 만들지 않고 `design-doc` 실행을 요청한다.
- Git remote·branch, profile, deployment처럼 현재 자료에서 확인하지 못한 값은
  사용자 질문 예산 안에서 확인하거나 `미정 — 현재 근거 없음`으로 표시한다.
- `local/dev/prod` profile과 `dev/main` branch 매핑은 사용자가 별도 기준을 주지 않았을
  때의 문서 기준이다. 존재를 확인하지 못한 외부 환경이나 branch를 실제 운영 중이라고
  단정하는 근거가 아니다.

## 관찰 기반 입력

`harness-bootstrap`이 전달한 코드 인벤토리는 현재 소스·설정에서 다시 확인할 수 있는
관찰 사실로 사용한다. 설계 의도와 Git·운영 정책을 추측하지 않으며, 규범 근거가 없는
금지 사항은 instruction에서 `미정`으로 남긴다.
