# 프로젝트 전체 DESIGN 작성 규칙

프로젝트 전체 스케일의 `DESIGN.md`를 처음 작성하거나 기존 문서를 갱신할 때 사용한다.
이 문서는 앱을 조기에 고정하는 상세 명세가 아니라, 앱의 현재 상위 구조를 공유하고
세부 설계 문서가 연결될 자리를 제공하는 기준 문서다.

## 라우팅 표

| 상태 | 적용할 섹션 |
|---|---|
| 기존 `DESIGN.md`가 없음 | [최초 작성] |
| 기존 `DESIGN.md`가 있음 | [기존 문서 갱신] |
| 직접 호출 또는 상위 스킬의 자동 호출 | 같은 상태별 절차 적용 |

## 공통 경계

- `02. 구축 대상 기능 분류`는 탐색용 분류 체계다. 여기에 없는 기능이라는 이유로
  상세 설계, 구현 지침서 또는 소스 변경을 막지 않는다.
- 최초 문서의 빈 하위 목록은 미정 세부사항을 나중에 확장할 자리다. 필수 구현 목록이나
  완료 조건으로 해석하지 않는다.
- 개요와 기능 분류를 확정하기 위해 상세 기능, 화면, 인터페이스, 완료 조건을 캐묻지 않는다.
- 확인된 사실과 사용자가 확정한 내용만 정본에 쓴다. 제안은 초안에서 구분한다.
- `DESIGN.md`는 현재 기준 스냅샷이다. 변경 전 값, 삭제·이동·이름 변경 기록,
  날짜별 경과, 의사결정 로그와 과거 대안은 본문에 남기지 않는다.
- 변경 내용과 이유는 검토·저장 승인 화면에서만 보여준다. 승인 뒤 저장하는 본문에는
  확정된 현재 값만 반영한다.
- 상세 설계가 앱의 목적이나 상위 기능 분류를 넓히면 다음 갱신 때 반영할 수 있지만,
  정본 갱신 전에도 그 상세 문서를 생성할 수 있다.
- `04. 아키텍처`의 패턴은 상위 구조 방향만 공유한다. 패키지·파일 구조 예시에 없는
  파일이라는 이유로 상세 문서나 구현을 막지 않으며, 예시는 파일 허용 목록이 아니다.

## 최초 작성

1. 프로젝트명, 매니페스트, README, 상위 요구사항과 디렉토리 구조에서 앱의 종류,
   사용 환경, 제공 가치와 기술 스택을 찾는다.
2. 앱의 정체성을 추론할 근거가 부족할 때만 대분류 수준으로 한 번 묻는다. 세부 기능이나
   성공 기준을 확정하는 질문은 하지 않는다.
3. `01. 개요`는 앱이 무엇을 제공하는지 현재 확인된 범위에서 2~3개 문단으로 쓴다.
   마지막에는 하위 분류와 상세 구현이 개발 과정에서 보완될 수 있음을 밝힌다.
4. `02. 구축 대상 기능 분류`에는 확인 가능한 대분류만 두고 각 대분류 아래에 빈 목록
   항목을 하나 둔다. 근거 없이 대분류를 발명하지 않는다.
5. `03. 기술 스택`에는 확인된 기술과 버전만 적는다.
6. `03. 기술 스택`을 근거로 적합한 상위 아키텍처 패턴을 먼저 제시한다. MVC·MVP·
   MVVM·계층형·헥사고날처럼 이름이 알려진 패턴도 기술 스택과 앱 성격에 실제로 맞는
   경우에만 후보로 든다. 프레임워크의 기본 구조, UI와 도메인 로직의 분리 필요성,
   서버·클라이언트 구성, 기존 코드 구조를
   근거로 권장안과 실제로 비교할 가치가 있는 대안만 설명한다. 패턴 이름만 나열하지
   말고 각 안이 만들어내는 패키지·파일 구조를 `text` 트리 예시로 함께 보여준 뒤 다음과
   같이 한 번 묻는다.

   > "기술 스택과 현재 구조를 보면 `[권장 패턴]`을 우선 권합니다. 대안은
   > `[대안 패턴]`이며, 각 패턴의 패키지·파일 구조 예시는 위와 같습니다.
   > 어떤 패턴을 적용할까요? 수정할 구조가 있으면 함께 알려주세요."

   상위 workflow가 같은 기술 스택을 근거로 후보·구조 예시를 보여주고 사용자의 선택을
   이미 받았다면 그 결과를 재사용하고 질문하지 않는다. 사용자가 선택하기 전에는
   추천안을 확정 구조로 기록하지 않는다. 선택하지 못하면
   `미정 — 사용자 선택 필요`로 남긴다. 선택한 패턴,
   기술 스택에 따른 현재 선택 근거와 패키지·파일 구조 예시를
   `04. 아키텍처`에 기록한다. 구조 예시는 별도 파일 규칙이 확정되기 전까지 설명용이다.
7. `05. 애플리케이션 특이사항`에는 다른 고정 섹션에 속하지 않는 앱 고유 사실과
   경계·연동·운영 제약을 모은다.
8. 배포 정보가 문서나 코드로 확정되지 않았으면 다음 내용을 한 번에 묻는다.

   > "로컬 개발 환경, 개발 서버 환경, 운영 환경을 각각 어떻게 구성할 예정인가요?
   > 환경별 서버 형태(클라우드·물리 서버 등), 운영체제, 배포·실행 방식
   > (컨테이너·JAR·정적 배포 등)을 알려주세요. 아직 모르면 배포 환경은 비워 두겠습니다."

   사용자가 모른다고 답하면 `06. 배포 환경` 제목만 유지하고 본문을 비운다.
9. `07. VSCode 익스텐션 추천`은 별도 질문 없이 기술 스택과 파일 형식에 맞춰 5개
   이내로 작성한다.

## 기존 문서 갱신

1. 기존 `DESIGN.md` 전체를 먼저 읽되 현재 사실 후보를 찾는 입력으로만 사용한다.
   기존 문서에 적혀 있다는 이유만으로 현재 사실로 간주하지 않는다.
2. 현재 사용자 확인과 현재 코드·설정·운영 문서를 우선해 각 항목의 유효성을 판정한다.
   서로 충돌하거나 현재 여부를 확인할 수 없는 기존 내용은 초안 검토에서 알리고 정본
   본문에는 남기지 않는다.
3. 기존 제목이 달라도 현재 유효한 내용을 의미 기준으로 고정 목차에 배치한다. 기존 `주의사항`의
   내용 중 앱 고유 사실은 `05. 애플리케이션 특이사항`으로 옮긴다.
4. `02. 구축 대상 기능 분류`를 먼저 읽고, 앱의 주된 목적·사용자·상위 범위가 달라질
   때만 `01. 개요`를 추가하거나 수정한다.
5. 직접 재호출과 상위 스킬의 자동 호출 모두에서, 쓰기 권한 여부와 관계없이 갱신
   초안을 만들 수 있으면 개발자에게 다음 한 가지를 묻는다.

   > "구축 대상 기능 분류를 이번에는 몇 단계 깊이까지 정리하고, 어떤 분류로
   > 추가·이동·이름 변경할까요? 유지할 기존 노드도 함께 알려주세요."

6. 답변과 확인된 자료를 반영해 현재 기능 노드만 남긴다. 추가·이동·이름 변경·제거와
   그 이유는 검토용 변경 요약에서만 보여주고 `DESIGN.md` 본문에는 기록하지 않는다.
7. 기술 스택이나 기존 구조가 달라져 현재 아키텍처 근거가 유효하지 않으면 최초 작성과
   같은 방식으로 권장안·대안·패키지 또는 파일 구조 예시를 먼저 보여주고 선택을 다시
   확인한다. 현재 패턴과 근거만 기록하고, 과거 패턴과 검토했던 대안은 남기지 않는다.
   변화가 없으면 기존 선택을 반복해서 묻지 않는다.
8. 새 목차에 바로 대응하지 않는 기존 앱 고유 내용은 현재 유효한 경우에만
   `05. 애플리케이션 특이사항`에 둔다. 중복과 더 이상 유효하지 않은 내용은 제거하되
   제거 사실을 본문에 기록하지 않는다.
9. 배포 환경은 현재 확인된 사실만 갱신한다. 기존 값의 현재성을 확인할 수 없으면
   검토용 변경 요약에서 알리고 본문을 비운다.
10. VSCode 추천은 현재 기술 스택에 맞는 항목만 5개 이내로 남긴다. 교체 이력은 쓰지 않는다.

## 현재 사실 판정

다음 우선순위로 현재 기준을 판정한다.

1. 사용자가 이번 실행에서 명시적으로 확정한 내용
2. 현재 코드·매니페스트·설정·배포 파일과 현재 운영 문서에서 확인한 사실
3. 위 근거와 충돌하지 않고 현재성도 확인된 기존 `DESIGN.md` 내용

본문은 현재 상태를 직접 서술한다. `이전에는`, `변경했다`, `제거했다`, `옮겼다`,
`과거 버전`, `변경 이력`처럼 문서 변천을 설명하는 표현은 사용하지 않는다. 현재 파일에
남아 있는 잘못된 명칭이나 현재 운영 중인 호환 처리는 그 상태 자체가 현재 사실인 경우에만
직접 서술한다.

## 권한 정책이 있을 때

- 직접 호출과 상위 스킬의 자동 호출 모두 같은 병합 절차를 사용한다.
- 쓰기 권한이 없거나 guard가 저장을 허용하지 않아도 분석과 병합 초안은 대화창에
  반환한다. 권한을 우회하거나 정책을 바꾸지 않는다.
- 실제 파일 반영은 `design-doc`의 일반 저장 승인과 앱 핵심 문서 별도 확인을 모두
  통과한 경우에만 수행한다.
