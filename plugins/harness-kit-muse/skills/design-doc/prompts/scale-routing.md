# 스케일 라우팅 (scale-routing)

스케일 선택에 따라 사용할 INPUT / OUTPUT 양식과 활성화할 섹션을 결정한다.

---

## 스케일별 양식 매핑

| 스케일 | INPUT 양식 | OUTPUT 양식 | 비고 |
|--------|-----------|------------|------|
| 프로젝트 전체 | 대화형 최소 확인 | PROJECT_DESIGN | 앱 기준 문서 |
| 화면 단위 | INPUT_V2 | OUTPUT_V2 | 권장 |
| 기능 단위 | INPUT_V2 | OUTPUT_V2 | 권장 |
| 컴포넌트 / 로직 단위 | INPUT_V2 | OUTPUT_V2 | 권장 |
| 프로젝트 전체 (레거시) | INPUT_V1 | OUTPUT_V1_deprecated | ⚠️ deprecated — 레거시 호환 시에만 |

---

## 프로젝트 전체 라우팅

- `prompts/project-design.md`에서 최초 작성과 기존 문서 갱신을 구분한다.
- `templates/PROJECT_DESIGN.md`의 고정 목차를 사용한다.
- 상세 기능·화면·인터페이스를 확정하는 INPUT_V2 인터뷰는 진행하지 않는다.
- `02. 구축 대상 기능 분류`는 후속 문서와 구현을 제한하는 허용 목록이 아니다.

## 상세 설계 섹션 활성화 규칙

아래 규칙은 화면·기능·컴포넌트·로직 단위에서 `OUTPUT_V2`를 사용할 때 적용한다.

### 🔵 모든 스케일 공통
- A. 한 줄 요약
- B. 문제와 목적
- D. 범위
- E. 동작 흐름
- G. 집중할 로직
- H. 뒤집기 확인
- I. 열린 질문

### 🟠 화면 / 기능 / 컴포넌트 전용
- C-2. 기존 코드 컨텍스트
- F-2. 인터페이스 경계
- OUTPUT 04. 인터페이스 설계
- OUTPUT 08. 엣지 케이스 & 에러 처리
- OUTPUT 09. 테스트 시나리오

## 스케일 판단 가이드

사용자 발화가 모호한 경우 아래 기준으로 판단하여 확인한다.

| 발화 예시 | 판단 스케일 |
|-----------|------------|
| "온보딩 화면 설계해줘" | 화면 단위 |
| "로그인 기능 설계해줘" | 기능 단위 |
| "이 컴포넌트 어떻게 짜면 돼?" | 컴포넌트 단위 |
| "프로젝트 전체 설계해줘" | 프로젝트 전체 — PROJECT_DESIGN |
